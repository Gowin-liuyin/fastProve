# 判定：问题出在方案，还是出在我们的实现？

**结论先行：方案本身有问题，我们的实现没有问题**（详见 §9 最终判定、
§8.1 归属总表、§7 实现侧对抗性自审）。

> 背景：ρ 泄漏 `‖h‖`、可恢复输入 token 的问题（见 `docs/problem_analysis.md`、
> `docs/PROBLEMS.md` §1.1）曾反馈给上游（Aloepri 团队），但对方"没有找到"。
> 本文逐条核对方案手册（《链式 LWE 噪声协变混淆实验系统开发手册》）原文，
> 给出一个可检验的判定：**哪些通道是方案强制的，哪些才是我们实现的选择**，
> 并解释为什么上游靠代码审查找不到它。
>
> 原则：所有数字转引自 `docs/PROBLEMS.md` 的 recorded run，不引入新数字。
> 手册引用格式：§章节号（手册 markdown 行号）。

## 0. 判定结论

**核心通道是方案强制的，不是实现引入的。**

手册自己规定了三件事，这三件事合起来**逻辑上必然**产生泄漏通道：

1. §81（行 2643–2646）：`RMSNorm：提取正交信号，噪声不进入范数`
   → ρ 必须是**纯信号**的 RMS，一点噪声都不能掺；
2. §38（行 1557、1564–1570）：`RMS 统计: FP32`，且明确列出 RMS 统计
   **不能**用 BF16 → ρ 必须算得**足够精确**；
3. §14.1（行 643–647）：`h₀ = E[t]`，E 是基座 embedding 表 → 第 0 层信号
   **就是公开表的一行**。

由 1+2：ρ = rms(h) 精确成立 ⟹ `‖h‖² = (ρ²−eps)·d` 精确成立。
由 3：第 0 层的 `‖h₀‖` 是**逐 token 常量**，而基座公开 ⟹ 攻击者离线建
"范数 → token"查找表。

**任何**忠实实现这份手册的系统——不管谁写、用什么语言、什么 kernel——
都存在这条通道。它不是我们代码里的 bug。

## 1. 逐条推导：为什么"任何忠实实现"都逃不掉

### 推导链 A：ρ 指纹（最严重通道）

```
手册 §81      噪声不进入范数        ⟹  ρ = rms(h_signal)，精确
手册 §38      RMS 统计必须 FP32     ⟹  ρ 的精度足以支持查表
代数恒等式    ρ² = ‖h‖²/d + eps     ⟹  ‖h‖ 由 ρ 唯一确定
手册 §14.1    h₀ = E[t]             ⟹  第 0 层 ‖h₀‖ 是逐 token 常量
公开基座      E 可离线获取           ⟹  "范数 → token" 查找表可离线构建
──────────────────────────────────────────────────────────────────
结论：服务端只要算对 RMSNorm（手册强制），输入 token 就以
      92.5%（Qwen2-1.5B）/ 93.4%（Llama-3.2-3B，FP32）被唯一恢复。
```

实测支撑：`results/raw/token_recovery_from_rho.json`、
`results/raw/token_recovery_from_rho_llama.json`（PROBLEMS.md §1.1）。

**攻击成本核对**（这是"方案问题"的最强证据）：

| 攻击需要 | 手册是否禁止能阻止它 |
|---|---|
| 已知明文对 (h, c) | 无关——攻击根本不用 c |
| 知道秘密矩阵 M | 无关——不用 M |
| 修改 kernel / 读寄存器 | 无关——见推导链 B，从输出反推 |
| 公开 base checkpoint | 手册无法禁止（主流基座本来就开源） |

手册里**没有任何条款**能切断这条链，因为链的每一环都是手册自己要求的。

### 推导链 B：融合内核辩护失效（ρ 从必须存在的输出反推）

手册 §15.4（行 751–764）的辩护是：把"信号提取 → RMSNorm → Q/K/V"融合在
一个流程里，中间值不写回显存，服务器"看不到"。

但手册 §43（行 1701–1720）同时**强制**融合内核输出 `query`。于是：

```
Q = (c · W̃_q) / ρ        （W̃_q 是部署权重，服务端必然持有；c 是服务端输入）
        ⟹  ρ = (c · W̃_q) / Q       （一次逐元素除法）
```

ρ 由**必须同时存在的输入和输出**代数地确定，与"是否写回显存"无关，
与融合与否无关，与谁实现无关。实测：Q 用 FP32 输出时反推 `‖h‖`
相对误差 1.45e-08（`results/raw/rho_recoverable_from_fused_output.json`，
PROBLEMS.md §1.2 / threat_model 5bis.10）。

注意手册 §21.3（行 968–974）自己承认的边界是"若服务器能**修改 kernel
并主动导出寄存器**中的 A"。推导链 B 比这个边界更糟：**零特权、零修改**，
只需要服务端本来就要算的数。这是手册威胁模型表述的层次遗漏
（详见 `docs/problem_analysis.md` §3.5）。

### 推导链 C：正确性测试通过 ⟹ 恰恰证明通道存在

这是解释"上游找不到"的关键，也是最反直觉的一点：

```
手册 §62–§67 的验收标准：混淆输出与明文输出逐位/逐 token 一致（100% match）
        ⟹  RMSNorm 算对了
        ⟹  ρ 算对了
        ⟹  ‖h‖ 指纹存在且精确
```

**测试全绿不是"没问题的证据"，而是"通道存在"的证明。**
一个把 ρ 算错的实现（噪声掺进范数、精度不足）反而会让这些测试失败。
所以靠跑测试套件、做代码审查、查数据流方向，都**原则上**找不到这个问题——
它不在"实现偏离设计"的方向上，而在"设计本身"里。

### 推导链 D：上游当前处境的两难分支

从上游自己的审计文档（`strict_method_audit.md`）看，其 canonical 路径用
"扩维 RMS（D = d+2h）"。这形成一个只有两个分支的两难：

- **分支 1：噪声/扩维坐标进入范数** → 违反手册 §81 的 boxed 原则
  （"任何安全变换都不能改变原模型的真实信号计算"）→ 模型算错。
  与其实测一致：logits 最大误差 19.83–28.82、argmax 匹配 **0/4**、
  8 题任务 smoke 明文 87.5% vs 混淆 12.5%。
- **分支 2：把范数修正为纯信号 RMS（按手册 §81 办）** → 正确性恢复，
  但推导链 A 立即生效，ρ 指纹通道全开。

（此段对上游内部实现的推断基于其审计文本，需其确认；但两难本身
不依赖推断——手册的两条要求 §81 与"正确性"在公开基座下不可兼得。）

**这解释了"他们没有找到"的最可能原因：他们还在分支 1 里修正确性。
一个连输出都不对的系统，没人会去测"攻击者能从它恢复什么"。**
等他们把正确性修好（进入分支 2），通道就会在他们自己的系统上出现。

## 2. 诚实的区分：哪些确实是我们实现的选择

判定要公平。以下几条**不是**方案强制的，是我们仓库的实现/超参选择，
换一种实现可以避免或削弱（但核心通道仍在）：

| 通道 | 归属 | 说明 |
|---|---|---|
| **块对角基降低 KPA 代价**（§2.2） | 半固有 | 手册 §10 推荐"小块正交矩阵"结构，块宽 b 是我们选的 |
| **辅助噪声 98% 是 h 的线性像**（§1.7） | **我们的超参选择** | C/ξ 尺度比可调；但受 §2.1 的 `‖e‖/‖h‖ ≤ 30` FP32 上界约束 |
| **tied embedding 内存膨胀**（§2.4） | 模型属性 + 我们的 `untied_deployed` 选择 | 与泄漏无关，是开销问题 |
| **eager 参考实现使攻击更容易** | 实现现状 | 参考实现中 ρ/Q 是普通张量，攻击比手册设想的融合场景更容易。但 §1.2 已证明融合也挡不住，这只影响攻击难度，不影响判定 |

**归属修正（2026-09-14 对账后）**：此前把 **Gram 成对几何精确暴露**
（PROBLEMS §1.4）归为"我们的实现选择"。逐行核对 `src/fastprove/structured.py`
与 `scripts/verify_gram_leakage.py` 后修正为**方案强制**：

- 任何精确计算 ρ 的实现都必须把二次型 `A = PPᵀ` 交给服务端（O(n²) 稠密
  二次型违反 ≤5% 开销目标，块对角只是满足开销约束的"便宜形状"）；
- 成对内积/距离由 A 唯一确定（`⟨hᵢ,hⱼ⟩ = cᵢAcⱼᵀ`），与块的形状无关；
- `verify_gram_leakage.py` 用完整 `PPᵀ` 做恢复是忠实的：服务端持有的
  块 + `perm_out` 可以精确重组出完整 Gram（`_gram_blocks_from` 在转换期
  强制校验非对角残差 ≤1e-9，块对角性是精确性质而非近似）。

而以下几条是**方案强制**的（手册原文直接规定）：

| 通道 | 手册依据 |
|---|---|
| ρ = rms(h) 精确、噪声不进范数 | §81（行 2643–2646）boxed 原则 |
| ρ 必须 FP32 精度 | §38（行 1557、1564–1570） |
| 第 0 层信号 = 公开 embedding 行 | §14.1（行 643–647） |
| 融合内核必须输出 Q | §43（行 1701–1720）接口签名 |
| QK 分数与明文完全一致（排序结构可见） | §20（行 897–917）：`S = S_plain` |
| 链式噪声衰减 G = γP（⟹ N 进部署权重，§1.6） | §12（行 548–590） |
| 实数可逆混合（⟹ h 无损编码于 c，§1.5） | §9/§11（行 391–422、462–543） |
| 客户端在线只编解码（⟹ ρ 计算无法移回客户端） | §5 原则三（行 241–263） |

## 3. 为什么上游团队"没有找到"

四个原因，按可能性排序：

1. **找错了层。** 他们在找"实现 bug"——置换方向、dtype、κ 尺度、数据流。
   这类问题的特征是"测试失败"。而 ρ 通道的特征恰恰相反：
   **测试全绿时它必然存在**（推导链 C）。用找 bug 的方法找构造缺陷，
   方法论上就找不到。
2. **正确性还没闭环。** 其当前主路径 argmax 匹配 0/4、任务 smoke 12.5%，
   注意力全部在修 κ 尺度矛盾（其审计自述"未归因、未解决"）。
   安全分析通常在正确性之后做——他们还没走到那一步。
3. **攻击需要主动对抗实验。** 标准测试套件（其 373 个测试）验证的是
   "混淆输出 = 明文输出"；"建范数→token 查找表并统计恢复率"不在任何
   正确性测试的形状里。我们自己也是专门写了
   `scripts/verify_token_recovery_from_rho.py` 才量化的。
4. **威胁模型表述误导了搜索方向。** 手册 §21.3 把安全边界写成
   "若服务器能修改 kernel 并主动导出寄存器"——这让人以为风险需要
   特权访问。而真实通道（推导链 B）从必须存在的输出反推，零特权。
   搜索"如何防住特权攻击者"不会命中"无需特权的反推"。

**补充（2026-09-14 对账后）**：还有一个我们侧的原因——§4.3 的 τ-sweep
缓解数字当时缺 raw 工件（见 §7.2-A），上游拿到的是无法从工件复现的数字，
这会直接削弱"问题真实存在"的可信度。

## 4. 给上游的最小自验实验

下面的实验**不需要我们的任何代码**，在他们自己的 Qwen2.5-0.5B 栈上
即可复现核心机制。它只用到：公开 embedding 表 + 手册自己要求的
"RMSNorm 算对且 FP32"。

```python
import torch
from transformers import AutoModelForCausalLM

m = AutoModelForCausalLM.from_pretrained("<本地 Qwen2.5-0.5B 路径>")
E = m.get_input_embeddings().weight.detach().float()  # 公开基座表
norms = E.norm(dim=1)                                  # 逐 token 指纹

torch.manual_seed(0)
tokens = torch.randint(0, E.shape[0], (4000,))

# 手册 §81 强制：ρ 是纯信号的 RMS；手册 §38 强制：FP32。
# 服务端要算对 RMSNorm，就必然知道（或可反推，见推导链 B）这个值：
rho = (E[tokens].pow(2).mean(-1) + 1e-6).sqrt().float()

# 攻击：范数最近邻查表（我们仓库的正式协议是排序+二分窗口，
# 见 scripts/verify_token_recovery_from_rho.py；此处是最小示意）
d = (norms[None, :] - rho[:, None]).abs()
pred = d.argmin(dim=1)
print("recovery@1 =", (pred == tokens).float().mean().item())
```

预期：若其 embedding 行范数高度互不相同（Qwen2-1.5B 为 99.05%，
Llama-3.2-3B 为 100%；0.5B 需实测），FP32 下恢复率应在 90%+ 量级。
**若他们跑出显著非零的恢复率，通道在其自己的构造上成立，争议即告终结。**

配套的两个追问实验（同样不需要我们的代码）：

1. **融合反推**：在其 fused RMS-QKV 的输出 Q 与输入 c、部署 W̃_q 上验证
   `ρ ≈ (c·W̃_q)/Q`（逐元素，取任一非零坐标）。若成立，"ρ 只在寄存器里"
   的辩护在其自己的实现上失效。
2. **两难确认**：问其一个二选一问题——"你们的 RMS 归一化因子是纯信号的
   函数，还是混入了噪声/扩维坐标？"前者 → 推导链 A 适用；后者 →
   违反其手册 §81，正确性不可能达标（与其 argmax 0/4 的实测一致）。

## 5. 沟通建议：如何回应可能的反驳

| 上游可能的反驳 | 回应 |
|---|---|
| "ρ 在融合内核寄存器里，读不到" | 推导链 B：ρ = (c·W̃_q)/Q，从必须输出的 Q 反推，零特权。实测 FP32 反推误差 1.45e-08 |
| "把 ρ 存成 BF16 就查不出来了" | BF16 下恢复率确实降为 0，但 4.7e-03 相对误差违反其自己的手册 §38（RMS 统计禁止 BF16）与正确性门禁——隐私失败换成正确性失败。且从 Q 反推的精度（7.9e-04）仍好于 BF16 ρ 自身精度 |
| "客户端多算几层就好了" | 实测深度不衰减：残差流保留 embedding 贡献，第 28 层稀有 token 范数预测仍 49.4%（基线 8.7%）（PROBLEMS §1.3 / 5bis.11） |
| "那是你们实现的问题" | 推导链 A 的每一环都是手册条款（§81、§38、§14.1）；通道不依赖 M、c、kernel、寄存器中的任何实现细节。请对方跑 §4 的 20 行实验 |
| "给 ρ 加噪声不就行了" | 那正是我们的 approximate 折衷（τ=1e-5，恢复率 93.8%→3.9%），但它**违反手册 §81 的 boxed 原则**（改变真实信号计算），等于放弃 exact 名分——这恰恰承认了问题在方案层：方案自己的原则内无解 |

最后一条值得展开：**"给 ρ 加噪声"不是反驳，而是让步。** 手册 §81 把
"不改变真实信号计算"列为最重要的正确性原则（boxed），ρ 是真实信号计算
的一部分。允许扰动 ρ = 承认 C1（输出精确）必须放松 = 承认四约束
（C1 输出精确 / C2 ≤5% 开销 / C3 无可信边界 / C4 隐藏输入）不可同时成立。
这正是 `docs/PROBLEMS.md` §5 的不可能三角——它是对**方案**的判定，
不是对**实现**的判定。

## 6. 一段话总结（可直接转给上游）

> 问题不在实现：我们的 303 个测试全绿、13 项独立 FP64 恒等式成立，
> 而泄漏通道恰恰在测试通过的系统上存在——因为手册 §81 要求"噪声不进入
> 范数"、§38 要求 RMS 用 FP32、§14.1 使第 0 层信号等于公开 embedding
> 的一行，三者合起来使 ρ = rms(h) 成为逐 token 指纹；§43 又强制融合
> 内核输出 Q，使 ρ 可由 (c·W̃_q)/Q 零特权反推。任何忠实实现该手册的
> 系统都有这条通道。你们目前没观察到它，是因为当前版本的归一化因子
> 混入了噪声坐标、正确性尚未闭环（argmax 0/4）——而按手册 §81 修好
> 正确性的那一天，就是通道全开的那一天。可用 20 行实验在你们自己的
> Qwen2.5-0.5B 上验证（见 §4）。

## 7. 实现侧对账：对抗性自审（2026-09-14）

判定要经得起反向检验：攻击脚本本身也可能高估或错报泄漏。我们把每个
攻击脚本与部署实现逐行对账，结果如下。

### 7.1 对账后确认无问题（实现不是原因）

| 检查项 | 结论 |
|---|---|
| Gram 块对角性 | **精确**而非近似：`structured.py` `_gram_blocks_from` 在转换期强制校验非对角残差 ≤1e-9，否则抛异常。`verify_gram_leakage.py` 用完整 `PPᵀ` 恢复是忠实的 |
| 融合反推实验的部署权重 | `verify_rho_recoverable_from_fused_output.py` 的 `absorbed @ q_math` 构造与 `layers/deployed.py` 真实构造逐项一致 |
| 真实权重交叉验证 | `pretrained_exact_mode_qwen_L4.json`：部署路径 logit 误差 6.9e-4、argmax 1.0 —— 部署路径确实算对了 ρ，`‖h‖` 指纹确实存在 |

### 7.2 我们实现/验证侧查出的三个真实问题

| # | 问题 | 严重性 | 修复方向 |
|---|---|---|---|
| A | **§4.3 的 τ-sweep 数字缺 raw 工件**。PROBLEMS.md §4.3 的缓解表（93.8%→3.9%、√L 缩放）只存在于文档散文；`eval_sweep_dtype_fixed.jsonl` 的 72 点是 Softmax logit 噪声 sweep，不是 ρ 噪声 sweep。违反我们自己的 recorded-run 规则。**这很可能就是上游"没有找到/不接受"的直接原因：我们给了无法从工件复现的数字** | 高 | 写正式 sweep 脚本 + raw JSON 落盘（复用 `run_accuracy_sweep.py` 骨架） |
| B | `verify_token_recovery_from_rho.py` 用 1 ulp 窗口建模 FP32 ρ，未计入 Gram 收缩的 FP32 误差（`‖e‖/‖h‖=1` 时约 4e-7，是 1 ulp 的 ~7 倍）。脚本**略微高估**攻击力 | 中 | 窗口并入 Gram 误差项；量级由 τ=0 实测 93.8% 交叉印证（依赖问题 A 补工件） |

### 7.3 对账后的最终判定

## 9. 最终判定（一句话汇总）

> **方案本身有问题，我们的实现没有问题。**
> 实现把方案忠实做出来了（303 测试全绿、13 项 FP64 恒等式、真实权重
> exact 门禁通过），方案把泄漏忠实做出来了（泄漏的每一环都是手册条款
> §81/§38/§14.1/§43 强制的）。问题不在"代码写错了"，在"方案的目标组合
> ——输出精确（C1）+ ≤5% 开销（C2）+ 无可信边界（C3）+ 隐藏输入（C4）
> ——数学上互斥"。要前进必须放弃其中一条：接受 approximate 模式（放弃
> C1，补测 τ=1e-5 任务精度）、引入可信边界（放弃 C3）、或换代数结构
> （放弃 C2）。实现侧仅有证据链缺口（§7.2-A）与攻击力小幅高估
> （§7.2-B），均不改变判定。
